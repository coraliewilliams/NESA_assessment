## Design decisions (proposed)

**JSONL — one line per student**, nested `courses[].exams[]`, mirroring the XML tree 1:1. Rationale: matches the natural streaming unit (whole `<student>` subtree parsed then discarded), needs zero joins to reconstitute, and avoids repeating 6 student-level fields across 4,898 mark rows in a text format that gets no columnar compression. Trade-off (stated explicitly): querying "all marks for course X" requires scanning+flattening every line — acceptable since JSONL here is an exchange/archival format, not a query layer.

**Parquet — single flat fact table at exam grain** (one row per exam/mark): `student_id, first_name, last_name, year_level, age, attendance_rate, socioeconomic_band, school, course_name, exam_seq, mark`. Rationale: the deliverable name is singular (`exams.parquet`), which rules out a multi-file normalised star schema; and Parquet's dictionary/RLE encoding makes repeating low-cardinality columns (school, course_name, band) across rows essentially free, so flattening costs little while making typical downstream queries (group-by course/school/band, no unnest) trivial in DuckDB/Spark/pandas — unlike nested list/struct columns, which would need explicit UNNEST in most engines for a single-file deliverable.

**M:N preservation:** student↔school is just multiple distinct `school` values under the same `student_id` — no junction table needed since there's no school metadata beyond the name; recoverable via `SELECT DISTINCT student_id, school`. No orphans possible because keys are derived positionally from the parse itself, not looked up against an external table.
